# IPsec Key Management, Oakley, and Internet Key Exchange (IKE)

## 1. Explanation
In IPsec, manual key management (where administrators manually configure keys and SPIs on every host) is feasible only in small, static test networks. In large-scale, enterprise, and internet-wide deployments, automated key exchange is mandatory. The standard automated key management protocol for IPsec is the **Internet Key Exchange (IKE)** protocol, which is a hybrid architecture combining the **Oakley Key Determination Protocol** and the **Internet Security Association and Key Management Protocol (ISAKMP)** (RFC 2408, RFC 2409, and IKEv2 RFC 7296).

### The Oakley Key Determination Protocol
Designed by Hilarie Orman, Oakley is a key exchange protocol based on the Diffie-Hellman algorithm, but refined to eliminate the classic vulnerabilities of unauthenticated Diffie-Hellman (such as Man-in-the-Middle attacks and denial-of-service clogging attacks).

#### Key Features of Oakley
1. **Cookies (Anti-Clogging Defense)**:
   - Before executing computationally intensive modular exponentiations, both parties exchange pseudo-random 64-bit numbers called **cookies** (nonces generated by hashing source/destination IPs, ports, and a secret local secret):
     $$\text{Cookie} = H(\text{Source IP} \parallel \text{Dest IP} \parallel \text{Source Port} \parallel \text{Dest Port} \parallel \text{Local Secret})$$
   - An attacker attempting to flood an IPsec gateway with fake Diffie-Hellman requests cannot spoof their source IP, because they must echo back the cookie sent to that IP before the gateway allocates cryptographic memory or CPU cycles.
2. **Support for Multiple Mathematical Groups**:
   - Allows negotiating algebraic groups: modular exponentiation groups ($\mathbb{Z}_p^*$) of varying prime sizes (Group 1: 768-bit, Group 2: 1024-bit, Group 5: 1536-bit, Group 14: 2048-bit) and Elliptic Curve groups ($\mathbb{F}_{2^m}$ and $\mathbb{F}_p$).
3. **Perfect Forward Secrecy (PFS)**:
   - Ensures that compromise of a long-term private key does not compromise previously established session keys.
4. **Three Authentication Methods**:
   Oakley provides three authentication options to thwart Man-in-the-Middle attacks:
   - **Digital Signatures**: Messages are authenticated by signing a mutually agreed exchange digest with the sender's private key.
   - **Public-Key Encryption**: Both parties encrypt their identity and authentication exchange using the peer's public key.
   - **Pre-Shared Key (Symmetric Secret)**: Authentication data is derived from an out-of-band shared secret key known only to the two peers.

### ISAKMP (Internet Security Association and Key Management Protocol)
Standardized in RFC 2408, ISAKMP provides a standardized framework and payload packet formatting for negotiating, establishing, modifying, and deleting Security Associations. ISAKMP defines payload types (SA, Proposal, Transform, Key Exchange - KE, Identification - ID, Certificate - CERT, Hash - HASH, Signature - SIG, Nonce - NONCE, Notification - NOTIFY, Delete - DELETE), but does not dictate a specific key exchange algorithm.

### Internet Key Exchange (IKE) Operation
IKE combines the framework of ISAKMP with the key exchange mechanisms of Oakley. IKE operates in **Two Phases**:

```
                  Two-Phase Operation of IKE
   [ PHASE 1: IKE SA Negotiation ]
   - Negotiates secure, authenticated control channel (IKE SA)
   - Uses Main Mode (6 messages) or Aggressive Mode (3 messages)
   - Authenticates endpoints and establishes shared master secret
                  │
                  ▼
   [ PHASE 2: IPsec SA Negotiation (Quick Mode) ]
   - Negotiates child SAs for AH and ESP traffic
   - All exchanges are encrypted and authenticated under IKE SA
   - Produces SPIs, keys, and algorithms for IPsec data packets
```

#### Phase 1: Establish the IKE SA (ISAKMP SA)
Establishes a secure, authenticated channel between the two IPsec peers. It can be executed in two modes:
1. **Main Mode (6 Messages)**:
   - *Messages 1 & 2*: Negotiate cryptographic security parameters (encryption algorithm, hash algorithm, authentication method, Diffie-Hellman group).
   - *Messages 3 & 4*: Perform the Diffie-Hellman key exchange (exchanging public values $Y_A, Y_B$ and nonces). Both compute the shared master secret `SKEYID`.
   - *Messages 5 & 6*: Exchange identity and authentication credentials (digital signatures or pre-shared key hashes). **These messages are encrypted**, keeping peer identities confidential from eavesdroppers.
2. **Aggressive Mode (3 Messages)**:
   - Compresses all negotiations into 3 messages for high speed.
   - Trade-off: Peer identities are transmitted unencrypted, exposing participant IDs to network eavesdroppers.

#### Phase 2: Establish the IPsec Data SAs (Quick Mode)
Negotiates the unidirectional child Security Associations for actual IPsec data traffic (AH or ESP).
- Typically requires only **3 messages**.
- All Quick Mode messages are encrypted and integrity-protected using keys derived in Phase 1 (`SKEYID_e` and `SKEYID_a`).
- Exchanges SPIs, selects IPsec protocol (AH vs ESP), confirms traffic selectors (SPD subnets), and derives IPsec operational symmetric keys.

## 3. Applications & Use Cases
1. **Automated Site-to-Site IPsec Tunnels**: Enterprise routers (Cisco ISR, Juniper SRX) maintain hundreds of dynamic IPsec tunnels using IKEv2, automatically renegotiating symmetric keys every 8 hours without manual administrator involvement.
2. **Mobile Device Telecommuting**: Laptops and smartphones connecting through IKEv2 MOBIKE (RFC 4555) retain active VPN sessions while switching between 4G/5G mobile data and Wi-Fi networks without dropping active IPsec SAs.

## 4. Solved Numerical / Analytical Examples

### Example 1: Derivation of Oakley Keying Material (`SKEYID`)
**Problem**:
In Oakley/IKE Phase 1 with Pre-Shared Key (PSK) authentication, explain how the master secret `SKEYID` and derived keys are calculated.

**Step-by-step Solution**:
- Let $g^{xy} \bmod p$ be the shared secret established via Diffie-Hellman.
- Let $N_i$ and $N_r$ be the nonces generated by initiator and responder.
- Let $K_{\text{psk}}$ be the pre-shared secret key.
- The master key `SKEYID` is computed as:
  $$\text{SKEYID} = \text{HMAC}(K_{\text{psk}}, N_i \parallel N_r)$$
- From `SKEYID`, three distinct subkeys are derived:
  1. `SKEYID_d` (Key Derivation Secret for Phase 2):
     $$\text{SKEYID}_d = \text{HMAC}(\text{SKEYID}, g^{xy} \parallel C_i \parallel C_r \parallel 0)$$
  2. `SKEYID_a` (Authentication Secret for Phase 1):
     $$\text{SKEYID}_a = \text{HMAC}(\text{SKEYID}, \text{SKEYID}_d \parallel g^{xy} \parallel C_i \parallel C_r \parallel 1)$$
  3. `SKEYID_e` (Encryption Secret for Phase 1):
     $$\text{SKEYID}_e = \text{HMAC}(\text{SKEYID}, \text{SKEYID}_a \parallel g^{xy} \parallel C_i \parallel C_r \parallel 2)$$

### Example 2: Cookie Verification Against SYN Flood Attacks
**Problem**:
Explain why the Oakley cookie mechanism is stateless on the responder side during initial handshakes.

**Step-by-step Solution**:
- If a responder stored state in memory upon receiving Message 1, an attacker could send thousands of Message 1 requests with spoofed source IPs, exhausting the responder's RAM.
- To prevent this, the responder computes:
  $$\text{Cookie}_B = \text{HMAC}(K_{\text{local\_secret}}, \text{IP}_{\text{src}} \parallel \text{IP}_{\text{dest}} \parallel \text{Port}_{\text{src}} \parallel \text{Port}_{\text{dest}} \parallel \text{Timestamp})$$
  and immediately sends it back in Message 2 **without storing any state in memory**.
- When the initiator returns $\text{Cookie}_B$ in Message 3, the responder recomputes the HMAC locally using its secret $K_{\text{local\_secret}}$. If it matches, the responder knows the initiator is at that IP and can receive packets; only then does it allocate memory state.

### Example 3: Comparison of IKE Phase 1 vs. Phase 2
**Problem**:
Summarize the differences between IKE Phase 1 and Phase 2.

**Solution**:
| Comparison Attribute | IKE Phase 1 (Main / Aggressive Mode) | IKE Phase 2 (Quick Mode) |
|---|---|---|
| **Purpose** | Establish a secure management tunnel (IKE SA). | Establish child data tunnels (IPsec SAs for AH/ESP). |
| **Traffic Carried** | Control, negotiation, and keying messages only. | Actual user and application data packets. |
| **Number of Messages** | 6 (Main Mode) or 3 (Aggressive Mode). | 3 (Quick Mode). |
| **Protection** | Starts in cleartext; ends with encrypted identity exchange. | Completely encrypted and authenticated under IKE SA. |
| **Lifetime** | Long-lived (typically 24 hours). | Shorter-lived (typically 1 hour or 1 GB of data). |

### Question 1 [KTU May 2019, Part A, Q8 - 4 Marks]
**Question**: Give the authentication methods used in Oakley algorithm.

**Solution**:
The Oakley key determination protocol provides three distinct authentication methods to authenticate Diffie-Hellman key exchanges and prevent Man-in-the-Middle (MITM) attacks:

1. **Digital Signatures**:
   - The exchange is authenticated by each party digitally signing an agreed-upon hash of the exchange parameters.
   - Specifically, each party signs a digest consisting of the source cookies, public Diffie-Hellman values, and nonces using their private asymmetric key (RSA or DSA):
     $$\text{Signature}_A = \text{Sign}_{PR_A}(H(\text{Cookie}_A \parallel \text{Cookie}_B \parallel g^a \parallel g^b \parallel N_A))$$
   - Each peer verifies the received signature using the other party's public key certificate. Provides origin authentication and non-repudiation.

2. **Public-Key Encryption**:
   - Each party encrypts their authentication exchange parameters (including their identity and unique nonces) using the recipient's public key (RSA or ElGamal).
   - Only the legitimate receiver holding the matching private key can decrypt and read the parameters, guaranteeing that the Diffie-Hellman values cannot be intercepted or modified by an attacker.
   - Provides identity protection in addition to mutual authentication.

3. **Pre-Shared Key (Symmetric Secret)**:
   - Both communicating parties possess an out-of-band pre-shared symmetric key $K_{\text{psk}}$ (configured manually or via out-of-band enterprise policy).
   - Authentication is achieved by calculating a keyed hash (HMAC) over the exchange components using the pre-shared key:
     $$\text{Auth} = \text{HMAC}(K_{\text{psk}}, \text{Cookie}_A \parallel \text{Cookie}_B \parallel g^a \parallel g^b)$$
   - Both peers verify the HMAC tag. Highly efficient for small enterprise deployments where maintaining a Public Key Infrastructure (PKI) is impractical.

### Question 2 [KTU May 2019 / January 2023 - 4 Marks]
**Question**: Explain the role of ISAKMP in IPsec key management.

**Solution**:
1. **Framework Definition**:
   The Internet Security Association and Key Management Protocol (ISAKMP, RFC 2408) provides a standardized framework, protocol state machine, and packet payload architecture for negotiating, establishing, modifying, and tearing down Security Associations (SAs) in IPsec.

2. **Decoupling Key Exchange from SA Management**:
   ISAKMP separates the architecture of Security Association negotiation from the details of specific key exchange algorithms. It does not mandate a single key exchange algorithm, but instead acts as a generic transport envelope that can carry Oakley, Diffie-Hellman, or other key agreement payloads.

3. **Standardized Payloads**:
   ISAKMP defines twelve modular payload types:
   - **SA Payload**: Initiates negotiation and declares proposals.
   - **Proposal & Transform Payloads**: Contain lists of supported algorithms (e.g., AES-256, HMAC-SHA256, DH Group 14).
   - **Key Exchange (KE) Payload**: Carries the public Diffie-Hellman key material.
   - **Identification (ID) Payload**: Identifies the peer (IP address, DNS name, email).
   - **Certificate (CERT) Payload**: Carries X.509 public-key certificates.
   - **Hash & Signature Payloads**: Provide message integrity and cryptographic authentication.
   - **Nonce Payload**: Contains pseudorandom nonces for anti-replay and key derivation.
   - **Notification & Delete Payloads**: Signal error conditions, status updates, or SA termination.
