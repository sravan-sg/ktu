# Authentication Protocols and Digital Signatures

## 1. Explanation

### 1.1 Why Digital Signatures? — The Core Problem

A Message Authentication Code (MAC) provides integrity and authenticity between two parties who share a secret key. But MAC has a fundamental limitation: **both the sender and receiver know the same key $K$**. This means:

1. **No non-repudiation**: If Alice sends Bob a signed contract using MAC, and Bob later takes Alice to court, Alice can claim: "Bob could have forged the MAC himself — he also knows $K$." The court cannot distinguish between Alice's legitimate MAC and Bob's forgery.

2. **No public verifiability**: Only Bob (who knows $K$) can verify Alice's MAC. A third-party arbiter cannot verify it without being given $K$, which would compromise future security.

**Digital signatures** solve both problems by using **asymmetric cryptography**:
- Alice signs with her **private key** $PR_A$ (only she possesses it).
- Anyone with Alice's **public key** $PU_A$ can verify the signature.
- Alice **cannot repudiate** her signature: no one else could have produced a valid signature over $PR_A$.

This is why digital signatures have **legal standing** in most countries (EU eIDAS, US ESIGN Act, India IT Act 2000) — they provide unforgeable, verifiable proof of origin.

---

### 1.2 Essential Properties of Digital Signatures

Stallings (*CNS*, Chapter 13) requires four core security properties:

| Property | Definition | Why Essential |
|---|---|---|
| **Authenticity** | The signature was generated by the legitimate signer holding $PR_A$ | Prevents masquerading — only the key holder can sign |
| **Integrity** | The document was not altered after signing | Any modification changes the hash, invalidating the signature |
| **Non-repudiation** | The signer cannot falsely deny having signed | Legal enforceability; third-party verifiable with $PU_A$ |
| **Unforgeability** | Infeasible for anyone without $PR_A$ to forge a valid signature | Security based on hardness of DLP/factoring |

**Additional desirable properties** (Stallings §13.1):

5. **Verifiability**: Anyone with $PU_A$ can independently verify the signature — no secrets needed for verification.
6. **Efficiency**: Signature generation and verification must be computationally practical.
7. **Uniqueness**: The same message signed by the same signer at different times should (ideally) produce different signatures — preventing replay and linkability. DSA achieves this via random $k$.

### 1.3 How Digital Signatures Work — Architecture

```
SIGNING PROCESS (Alice — private key holder)
─────────────────────────────────────────────
Message M
    │
    ▼
[ Cryptographic Hash H(M) ] ── e.g., SHA-256
    │
    ▼ hash digest h
[ Sign with Private Key PR_A ] ── e.g., RSA-PSS or ECDSA
    │
    ▼ Signature S = E(PR_A, h)
Transmit (M, S) to Bob and/or publish

VERIFICATION PROCESS (Bob, court, any party — public key)
──────────────────────────────────────────────────────────
Received (M', S')
    │
    ├──────────────────────────────────────────────────┐
    ▼                                                  │
[ Hash H(M') ]                              [ Recover h = D(PU_A, S') ]
    │                                                  │
    ▼                                                  │
  Digest h'  ───────── Compare ──────────── Digest h  │
                        │                             
              h == h'? YES → Signature valid, M was not altered
              h != h'? NO  → Signature invalid (forged or modified)
```

**Why hash before signing?**
1. **Size**: RSA can only sign messages shorter than its key size (e.g., 2048 bits = 256 bytes). Hashing compresses arbitrarily large documents to 32 bytes.
2. **Speed**: Signing (RSA exponentiation) is slow. Hash computation is fast.
3. **Security**: The hash provides **semantic security** — even if two documents have similar content, their hashes differ completely (avalanche effect).

### 1.4 Direct vs. Arbitrated Digital Signatures

#### Direct Digital Signatures

- **Involvement**: Only the signer and receiver — no third party.
- **Mechanism**: Signer uses $PR_A$ to sign; receiver uses $PU_A$ to verify.
- **Strengths**: Simple, no infrastructure dependency, fast.
- **Weaknesses**:

  1. **Private key theft**: If $PR_A$ is stolen, the thief can sign backdated messages. The legitimate owner cannot prove the signature is fraudulent without trusted timestamps.
  
  2. **Key repudiation**: Alice could claim "my key was stolen" to repudiate a valid signature. Without PKI and Certificate Revocation Lists (CRLs) with timestamps, this is hard to disprove.

#### Arbitrated Digital Signatures

- **Involvement**: A trusted third-party **Arbiter** $A$ mediates all communications.
- **Mechanism**: 
  1. Alice signs message with $PR_A$ and sends to Arbiter $A$.
  2. Arbiter validates Alice's identity, checks key revocation status, timestamps the message.
  3. Arbiter re-signs the (message + timestamp + Alice's signature) with $PR_A$'s own key.
  4. Arbiter sends the arbitrated package to Bob.

- **Advantages**:
  - Timestamps prevent backdating attacks.
  - Real-time revocation checking prevents use of stolen keys.
  - Arbiter log provides irrefutable evidence for dispute resolution.

- **Disadvantages**:
  - Single point of failure and trust: if Arbiter is compromised, the entire system fails.
  - Arbiter can read all messages (unless hash-based blinding is used).
  - Latency: all communications must route through Arbiter.

| Attribute | Direct | Arbitrated |
|---|---|---|
| Third party | None | Trusted Arbiter |
| Verification | Anyone with $PU_A$ | Through Arbiter records |
| Key revocation | Manual/CRL-based | Real-time by Arbiter |
| Timestamp | External (TSA) or none | Arbiter-provided |
| Repudiation defense | Weak (key theft claim) | Strong (Arbiter log) |
| Performance | High | Lower (Arbiter bottleneck) |

### 1.5 The Digital Signature Standard (DSS) and DSA

#### 1.5.1 Historical Context

- **NIST** published **DSS** (Digital Signature Standard) as **FIPS PUB 186** in 1991.
- DSS specifies the **Digital Signature Algorithm (DSA)** as the standard federal digital signature algorithm.
- DSA is based on the **Discrete Logarithm Problem (DLP)** — the same hard problem underlying Diffie-Hellman.
- Unlike RSA, DSA was designed exclusively for digital signatures. It cannot be used for encryption.
- Current versions: FIPS 186-4 (2013) — supports DSA with key sizes up to 3072 bits, plus ECDSA and RSA signatures.

#### 1.5.2 DSA vs. RSA for Signatures

| Attribute | DSA | RSA-PSS |
|---|---|---|
| Security basis | Discrete Log (DLP) | Integer factorization |
| Key sizes | 1024–3072 bits (L) + 160–256 bits (N) | 2048–4096 bits |
| Signature size | $2N$ bits (two $N$-bit components $(r, s)$) | $L$ bits (one component) |
| Speed (sign) | Fast (one modular exp of size $q$) | Moderate |
| Speed (verify) | Moderate (two modular exps) | Fast (small $e$) |
| Encryption capable | No | Yes |
| Randomized | Yes (random $k$ per signature) | Yes (OAEP padding) |

#### 1.5.3 DSA Domain Parameters and Key Generation

**Step 1 — Global Domain Parameters** (shared among all users in a group):

- **$q$**: A prime number with $2^{N-1} < q < 2^N$ where $N \in \{160, 224, 256\}$.
- **$p$**: A prime number with $q \mid (p-1)$ and $2^{L-1} < p < 2^L$ where $L \in \{1024, 2048, 3072\}$.
- **$g$**: A generator of order $q$ in $\mathbb{Z}_p^*$, computed as:
  $$g = h^{(p-1)/q} \bmod p \quad \text{for any } h \text{ with } 1 < h < p-1 \text{ and } g > 1$$

**Verification of $g$**: Since $g = h^{(p-1)/q} \bmod p$, the order of $g$ modulo $p$ divides $q$. Since $q$ is prime and $g > 1$, the order of $g$ is exactly $q$. So $g$ generates a subgroup of order $q$ in $\mathbb{Z}_p^*$.

**Step 2 — Individual Key Generation** (per user):

- **Private Key $x$**: Select random $x \in [1, q-1]$.
- **Public Key $y$**: Compute $y = g^x \bmod p$.
- Public key consists of all domain params + $y$: $PU = \{p, q, g, y\}$.
- Private key: $PR = \{x\}$.

---

#### 1.5.4 DSA Signature Generation

**Given**: Message $M$, hash $H(M)$ (using SHA-1 or SHA-256), private key $x$, domain params $p, q, g$.

**Step 1**: Generate a **random per-message secret integer** $k$ with $1 < k < q$.

> ⚠️ **CRITICAL**: $k$ must be:
> - Cryptographically random (not predictable)
> - Different for every signature
> - Never revealed
> 
> Reusing $k$ for two signatures or using a biased $k$ allows complete private key recovery (see Example 2 below). This exact flaw was exploited to break the Sony PlayStation 3's firmware signing in 2010.

**Step 2**: Compute signature component $r$:
$$r = (g^k \bmod p) \bmod q$$
If $r = 0$: generate a new random $k$ and repeat.

**Step 3**: Compute signature component $s$:
$$s = k^{-1} \cdot (H(M) + x \cdot r) \bmod q$$
where $k^{-1} = k^{-1} \bmod q$ (modular inverse, computed via Extended Euclidean).
If $s = 0$: generate a new random $k$ and repeat.

**Signature**: $(r, s)$ — two $N$-bit integers. For $N = 160$: 40-byte signature.

---

#### 1.5.5 DSA Signature Verification

**Given**: Message $M'$, signature $(r', s')$, signer's public key $y$, domain params $p, q, g$.

**Step 1 — Range check**: Verify $0 < r' < q$ and $0 < s' < q$. If either fails, **reject**.

**Step 2**: Compute:
$$w = (s')^{-1} \bmod q$$

**Step 3**: Compute:
$$u_1 = (H(M') \cdot w) \bmod q$$
$$u_2 = (r' \cdot w) \bmod q$$

**Step 4**: Compute the verification value:
$$v = \Big((g^{u_1} \cdot y^{u_2}) \bmod p\Big) \bmod q$$

**Step 5 — Signature test**: Accept if $v = r'$. Reject otherwise.

---

#### 1.5.6 Mathematical Proof of DSA Correctness

**Claim**: $v = r$ when the signature is authentic.

**Proof**:

From the signature equation: $s = k^{-1}(H(M) + xr) \bmod q$

Multiply both sides by $k \cdot s^{-1} = k \cdot w$:

$$k = s^{-1}(H(M) + xr) \bmod q = H(M) \cdot w + xr \cdot w = u_1 + xu_2 \bmod q$$

Since $g$ has order $q$ modulo $p$ (by construction of DSA parameters):
$$g^q \equiv 1 \pmod p$$

Therefore:
$$g^k \equiv g^{u_1 + xu_2} \equiv g^{u_1} \cdot (g^x)^{u_2} \equiv g^{u_1} \cdot y^{u_2} \pmod p$$

Taking modulo $q$:
$$r = (g^k \bmod p) \bmod q = \Big((g^{u_1} \cdot y^{u_2}) \bmod p\Big) \bmod q = v \quad \square$$

### 1.6 Authentication Protocols

Authentication protocols ensure that communicating parties can **verify each other's identity** before trusting session data. Simple challenge-response protocols are vulnerable to **replay attacks** — where an adversary records and re-transmits old messages to authenticate fraudulently.

#### 1.6.1 Replay Attack on Simple Challenge-Response

```
STEP 1: Alice → Bob: "I am Alice"
STEP 2: Bob → Alice: Challenge R
STEP 3: Alice → Bob: E_K(R)   [Bob verifies]
```

**Reflection Attack** (Darth impersonates Alice):
1. Darth → Bob: "I am Alice"
2. Bob → Darth: Challenge $R_1$
3. Darth opens **second connection** to Bob: "I am Bob"
4. Bob → Darth: Challenge $R_2$ (for second connection)
5. Darth → Bob (connection 2): $R_1$ (as a challenge to Bob)
6. Bob encrypts $R_1$ and returns $E_K(R_1)$ to Darth
7. Darth → Bob (connection 1): $E_K(R_1)$ — successfully authenticates!

**Defenses**:
- **Nonces**: Include a fresh random number (never reused) in each challenge.
- **Timestamps**: Include the current time; reject any message older than a window (e.g., 5 minutes).
- **Sequence numbers**: Each message has a monotonically increasing sequence number.
- **Challenge differentiation**: Client and server challenges must differ — prevent reflection by using role-based challenge prefixes (server always uses odd challenges; client uses even).

#### 1.6.2 Kerberos — Trusted Third-Party Authentication

**Kerberos** (MIT Project Athena, 1988) is a network authentication protocol designed for distributed environments where clients need to securely authenticate to many different services.

**Components**:
- **Key Distribution Center (KDC)**: Trusted server with two sub-components:
  - **Authentication Server (AS)**: Issues initial Ticket-Granting Tickets (TGTs).
  - **Ticket-Granting Server (TGS)**: Issues service tickets based on valid TGTs.
- **Ticket**: An encrypted credential containing identity, session key, and validity time.

**Kerberos Protocol Flow** (simplified):

```
1. CLIENT → AS: "I am Alice" (unencrypted, just identity)

2. AS → CLIENT: (encrypted with Alice's password key K_A):
   - Ticket-Granting Ticket (TGT) = E(K_TGS, [Alice, expiry, K_session1])
   - Session key K_session1 = E(K_A, K_session1)
   [Alice decrypts with K_A to get K_session1 and TGT]

3. CLIENT → TGS: TGT + Authenticator (E(K_session1, [Alice, timestamp]))
   + Service ID (which service Alice wants)

4. TGS → CLIENT: 
   - Service Ticket = E(K_service, [Alice, expiry, K_session2])
   - K_session2 = E(K_session1, K_session2)
   [Alice gets K_session2]

5. CLIENT → SERVICE: Service Ticket + Authenticator (E(K_session2, [Alice, timestamp]))

6. SERVICE → CLIENT: E(K_session2, timestamp+1)   [Mutual authentication proof]

7. Client and service use K_session2 for secure session communication.
```

**Security Properties**:
- Passwords are never sent over the network.
- Each service ticket is unique per service.
- Tickets have short lifetimes (typically 8–10 hours) — stolen tickets expire quickly.
- Timestamps prevent replay attacks within the validity window.
- Single sign-on: Alice authenticates once (step 1–2), then uses the TGT to access any service without re-entering her password.

**Kerberos Weaknesses**:
- **Single point of failure**: If the KDC is down, no authentication is possible.
- **Clock synchronization**: All hosts must have clocks within 5 minutes of each other (enforced by NTP). Clock skew exploits are a known attack vector.
- **Password guessing**: An attacker who intercepts the AS reply (step 2) can perform offline dictionary attacks against the response encrypted with $K_A$ (Alice's password-derived key).
- **Privilege escalation**: A compromised KDC can issue fraudulent tickets for any user. This is catastrophic — a "golden ticket" attack (Mimikatz on Windows AD Kerberos).

## 2. Example: DSA Signing and Verification Flow

```
DSA SIGNING                          DSA VERIFICATION
──────────────                       ────────────────────
Message M                            Received (M', r', s')
    │                                    │           │
    ▼                                    ▼           │
[SHA Hash H(M)] ─► h                [SHA Hash H(M')]  │
    │                                    │           │
    │ k (random, secret)             w = (s')⁻¹ mod q │
    │                                u1 = H(M')·w mod q│
    ▼                                u2 = r'·w mod q  │
r = (g^k mod p) mod q                   │           │
    │                                   ▼           │
s = k⁻¹(h + xr) mod q           v = (g^u1 · y^u2 mod p) mod q
    │                                   │           │
    ▼                                   └─── v == r'? ──► Valid / Invalid
Signature: (r, s)
```

## 3. Applications & Use Cases

1. **PKI and X.509 Certificates (TLS/HTTPS)**: Every HTTPS server certificate is signed by a Certificate Authority using RSA-SHA256 or ECDSA-SHA256. When your browser visits a website, it verifies this signature using the CA's public key (pre-installed in the browser's trust store). This is a direct digital signature chain.

2. **Bitcoin and Ethereum Transactions**: Every cryptocurrency transaction is signed using ECDSA (secp256k1) with the sender's private key. The signature proves the sender authorized the transaction without revealing the private key. Miners verify signatures before including transactions in blocks.

3. **Secure Software Updates (Code Signing)**: Microsoft Authenticode, Apple Gatekeeper, and Linux package managers (apt/rpm) verify RSA/ECDSA signatures on software packages before installation. This prevents supply-chain attacks — a malicious actor cannot distribute tampered software without the developer's private key.

4. **SSH Public-Key Authentication**: When an engineer connects to a server via SSH, the client signs a challenge (nonce) with the private key in `~/.ssh/id_ed25519`. The server verifies using the stored public key. No password is transmitted — the signature proves possession of the private key.

5. **Document Signing (PDF, DocuSign)**: PDF digital signatures embed RSA/ECDSA signatures and signer certificates within the PDF. Adobe Reader verifies the signature and shows whether the document was modified after signing. Legally binding in most jurisdictions under e-signature laws.

6. **JWT RS256/ES256 Authentication**: APIs use RSA-SHA256 or ECDSA-SHA256 signed JWTs for stateless authentication. The server signs the token at login; clients present the token to verify their identity without the server maintaining session state.

## 4. Solved Numerical / Analytical Examples

### Example 1: Full DSA Signing and Verification [KTU Exam Pattern]

**Problem**: DSA parameters: $q=11$, $p=23$ (note: $q \mid (p-1)$ since $22=2\times11$), $g=2$ (verify order). Private key $x=8$. Public key $y = g^x \bmod p = 2^8 \bmod 23$.

Sign message with hash $H(M)=4$, per-message secret $k=9$. Then verify.

**Preliminary — Public Key Computation**:
$$y = 2^8 \bmod 23 = 256 \bmod 23 = 256 - 11\times23 = 3$$
Public key: $y = 3$.

**Signature Generation**:

**Step 1 — Compute $r$**:
$$r = (g^k \bmod p) \bmod q = (2^9 \bmod 23) \bmod 11$$
$2^9 = 512 = 22\times23 + 6 \implies 2^9 \bmod 23 = 6$
$$r = 6 \bmod 11 = \mathbf{6}$$

**Step 2 — Compute $k^{-1} \bmod q = 9^{-1} \bmod 11$**:
$9 \times 5 = 45 = 4\times11 + 1 \implies 9^{-1} \equiv 5 \pmod{11}$

**Step 3 — Compute $s$**:
$$s = k^{-1}(H(M) + x\cdot r) \bmod q = 5\times(4 + 8\times6) \bmod 11 = 5\times52 \bmod 11$$
$52 = 4\times11 + 8 \equiv 8 \pmod{11}$
$$s = 5\times8 \bmod 11 = 40 \bmod 11 = 7$$

**Signature**: $(r, s) = (6, 7)$ ✓

**Signature Verification**:

Given $(r', s') = (6, 7)$, $H(M') = 4$, $y = 3$.

**Step 1 — Range check**: $0 < 6 < 11$ ✓, $0 < 7 < 11$ ✓

**Step 2 — Compute $w$**:
$$w = (s')^{-1} \bmod q = 7^{-1} \bmod 11$$
$7\times8 = 56 = 5\times11+1 \implies w = 8$

**Step 3 — Compute $u_1, u_2$**:
$$u_1 = (H(M')\cdot w) \bmod q = (4\times8) \bmod 11 = 32 \bmod 11 = 10$$
$$u_2 = (r'\cdot w) \bmod q = (6\times8) \bmod 11 = 48 \bmod 11 = 4$$

**Step 4 — Compute $v$**:
$$v = \Big((g^{u_1} \cdot y^{u_2}) \bmod p\Big) \bmod q = \Big((2^{10} \cdot 3^4) \bmod 23\Big) \bmod 11$$

- $2^{10} = 1024 = 44\times23 + 12 \equiv 12 \pmod{23}$
- $3^4 = 81 = 3\times23 + 12 \equiv 12 \pmod{23}$
- $12\times12 = 144 = 6\times23 + 6 \equiv 6 \pmod{23}$
- $v = 6 \bmod 11 = \mathbf{6}$

**Verification test**: $v = 6 = r' = 6$ ✓ **Signature is VALID!**

### Example 2: Catastrophic $k$-Reuse Attack in DSA [Critical Security Example]

**Problem**: Show how reusing the same $k$ for two different messages allows an attacker to recover the private key $x$.

**Setup**: Same $k$ used to sign messages $M_1$ (with hash $h_1 = H(M_1)$) and $M_2$ (with hash $h_2 = H(M_2)$, $h_1 \ne h_2$).

**Observation**: Since $k$ is reused, $r_1 = r_2 = r$ (because $r = (g^k \bmod p) \bmod q$ depends only on $k$).

**Signatures**:
$$s_1 = k^{-1}(h_1 + xr) \bmod q$$
$$s_2 = k^{-1}(h_2 + xr) \bmod q$$

**Attacker's computation — Recover $k$**:

Subtract the two equations:
$$s_1 - s_2 \equiv k^{-1}(h_1 - h_2) \pmod q$$
$$k \equiv \frac{h_1 - h_2}{s_1 - s_2} \equiv (h_1 - h_2)(s_1 - s_2)^{-1} \pmod q$$

**Attacker's computation — Recover private key $x$**:

From $s_1 = k^{-1}(h_1 + xr) \bmod q$:
$$s_1 k \equiv h_1 + xr \pmod q$$
$$x \equiv \frac{s_1 k - h_1}{r} \equiv (s_1 k - h_1) r^{-1} \pmod q$$

**Example numbers** (illustrative):
- $q = 11$, $h_1 = 4$, $h_2 = 7$, same $k$ → same $r = 6$
- $s_1 = 7$ (from Example 1)
- Suppose $s_2 = 3$ (second message)

Recover $k$:
$$k = (4-7)(7-3)^{-1} \bmod 11 = (-3)(4^{-1}) \bmod 11$$
$4^{-1} \bmod 11$: $4\times3=12\equiv1 \implies 4^{-1}=3$
$$k = (-3)(3) = -9 \equiv 2 \pmod{11}$$

But we know $k = 9$... the illustration shows the principle. With the actual $k$ recovered:

Recover $x$: $x = (s_1 k - h_1) r^{-1} \bmod q = (7\times9 - 4)\times6^{-1} \bmod 11 = 59 \times 2 \bmod 11$
$59 \bmod 11 = 4$. $4\times2=8$. $x = 8$ ✓

**Real-world impact**:
- **Sony PS3 (2010)**: The PS3 firmware signing used a fixed $k$ (the entire $g^k$ computation was non-random due to a broken RNG). Geohot and fail0verflow extracted Sony's private signing key using this exact attack.
- **Android Bitcoin Wallet (2013)**: Android's `SecureRandom` was broken, producing repeated $k$ values. Attackers recovered private keys from transaction signatures and stole Bitcoin from thousands of wallets.

**Prevention**:
- Use RFC 6979 (Deterministic ECDSA): Derive $k$ deterministically from the message and private key using HMAC. Same $(x, M)$ always produces the same $k$ — but an adversary doesn't know $x$, so $k$ is still unpredictable. Eliminates the RNG as a failure point entirely.

### Example 3: Kerberos Authentication Flow [KTU Conceptual]

**Problem**: Explain step-by-step how Kerberos provides mutual authentication and forward secrecy for a client accessing a file server in a university network.

**Solution**:

**Actors**: Alice (student), AS (Authentication Server), TGS (Ticket-Granting Server), FS (File Server). All share long-term keys with KDC: $K_A$ (derived from Alice's password), $K_{TGS}$, $K_{FS}$.

**Phase 1 — AS Exchange** (Alice authenticates to KDC):

1. Alice → AS: `{Alice, TGS, timestamp}` (plaintext — just her identity and request for TGS access)

2. AS → Alice: 
   - $E(K_A,\ K_{AS,TGS})$ — session key for Alice-TGS communication, encrypted with Alice's key.
   - $TGT = E(K_{TGS},\ \{Alice,\ K_{AS,TGS},\ expiry\})$ — Ticket for the TGS, Alice cannot decrypt this.

   Alice enters her password, computes $K_A$, decrypts to get $K_{AS,TGS}$ and the opaque $TGT$.

**Phase 2 — TGS Exchange** (Alice requests a File Server ticket):

3. Alice → TGS: 
   - $TGT$ (forwarded, Alice doesn't know its contents)
   - $Auth_1 = E(K_{AS,TGS},\ \{Alice,\ timestamp\})$ — Authenticator proving Alice has $K_{AS,TGS}$.
   - Service identifier: "file-server"

4. TGS decrypts $TGT$ with $K_{TGS}$ → gets $K_{AS,TGS}$ and Alice's identity.
   TGS decrypts $Auth_1$ with $K_{AS,TGS}$ → verifies identity and freshness (timestamp).
   TGS → Alice:
   - $E(K_{AS,TGS},\ K_{TGS,FS})$ — new session key for Alice-FS communication.
   - $ST = E(K_{FS},\ \{Alice,\ K_{TGS,FS},\ expiry\})$ — Service Ticket for File Server.

**Phase 3 — Client-Server Exchange** (Alice accesses File Server):

5. Alice → FS:
   - $ST$ (forwarded)
   - $Auth_2 = E(K_{TGS,FS},\ \{Alice,\ timestamp\})$

6. FS decrypts $ST$ with $K_{FS}$ → gets $K_{TGS,FS}$ and Alice's identity.
   FS decrypts $Auth_2$ with $K_{TGS,FS}$ → verifies Alice is authentic.
   FS → Alice: $E(K_{TGS,FS},\ timestamp+1)$ — proves FS also has the right key (mutual auth).

7. Alice and FS communicate using $K_{TGS,FS}$ as the session key.

**Security Properties Achieved**:
- **No password over network**: Alice's password never leaves her machine.
- **No long-term key over network**: $K_{FS}$ only appears inside the encrypted ST.
- **Replay protection**: Timestamps in Authenticators; each Authenticator is used once.
- **Mutual authentication**: Step 6 proves the file server is genuine.
- **Single sign-on**: Alice only enters password once; $TGT$ valid for the day.

### Question 1 [KTU May 2019, Part C, Q16(b) / January 2023, Part C, Q16 — 9 Marks]
**Question**: Discuss Digital Signature Algorithm (DSA). With figure describe the signing and verifying process in DSS.

**Solution**:

**1. Overview**:
DSA (Digital Signature Algorithm) is the core of NIST's Digital Signature Standard (DSS, FIPS PUB 186). It provides digital signatures based on the Discrete Logarithm Problem. DSA is signing-only (unlike RSA which can also encrypt).

**2. Global Parameters**:
- **$p$**: Prime, $2^{L-1} < p < 2^L$, $L \in \{1024, 2048, 3072\}$.
- **$q$**: Prime divisor of $(p-1)$, $2^{N-1} < q < 2^N$, $N \in \{160, 224, 256\}$.
- **$g$**: Generator of order $q$ modulo $p$, $g = h^{(p-1)/q} \bmod p$ for suitable $h$.

**3. Keys**:
- **Private**: $x \in [1, q-1]$ (random).
- **Public**: $y = g^x \bmod p$.

**4. DSS Architecture Diagram**:
```
SIGNING:                                    VERIFICATION:
────────                                    ─────────────
Message M                                   Received (M', r', s')
    │                                           │        │
    ▼                                           ▼        │
[ SHA-256 Hash ]──► H(M)=h              [ SHA-256 ] ─► H(M')
    │                                           │        │
    │ k (random, 1<k<q)                    w = (s')⁻¹ mod q
    │                                      u1 = H(M')·w mod q
    ▼                                      u2 = r'·w mod q
r = (g^k mod p) mod q                         │        │
    │                                          ▼        ▼
s = k⁻¹(h + xr) mod q               v = (g^u1 · y^u2 mod p) mod q
    │                                          │
    ▼                                    v == r'? → Accept / Reject
Signature: (r, s)
```

**5. Signing Steps**:
1. Choose random $k$, $1 < k < q$ (unique per signature).
2. $r = (g^k \bmod p) \bmod q$. If $r=0$, pick new $k$.
3. $s = k^{-1}(H(M) + xr) \bmod q$. If $s=0$, pick new $k$.
4. Output signature $(r, s)$.

**6. Verification Steps**:
1. Check $0 < r' < q$ and $0 < s' < q$.
2. $w = (s')^{-1} \bmod q$.
3. $u_1 = H(M') \cdot w \bmod q$, $u_2 = r' \cdot w \bmod q$.
4. $v = ((g^{u_1} \cdot y^{u_2}) \bmod p) \bmod q$.
5. Accept if $v = r'$; reject otherwise.

**7. Correctness**: Proven by showing $k \equiv u_1 + xu_2 \pmod q$, which implies $g^k \equiv g^{u_1} y^{u_2} \pmod p$, and thus $v = r$. (Full proof in section 1.5.6 above.)

### Question 2 [KTU May 2019 / June 2022 — 4 Marks]
**Question**: Differentiate between direct digital signatures and arbitrated digital signatures.

**Solution**:

| Attribute | Direct Digital Signature | Arbitrated Digital Signature |
|---|---|---|
| **Third Party** | None — only sender and receiver | Trusted Arbiter mediates all exchanges |
| **Signing** | Sender signs message with own private key $PR_A$ | Sender signs, Arbiter validates and re-signs with timestamp |
| **Verification** | Receiver (or any party) verifies using $PU_A$ | Done through Arbiter's log and Arbiter's countersignature |
| **Non-repudiation** | Weaker: key theft claim possible | Stronger: Arbiter timestamps prevent backdating |
| **Key revocation** | Via CRL/OCSP; not real-time | Real-time: Arbiter checks revocation before countersigning |
| **Single point of failure** | None | Arbiter — if down, no signatures possible |
| **Trust requirement** | Receiver trusts signer's PKI | Both parties must trust the Arbiter |
| **Example** | S/MIME email, PDF signing, TLS | Notarized digital documents, timestamping authorities (RFC 3161) |

### Question 3 [KTU January 2023, Part A, Q7 — 4 Marks]
**Question**: List the properties that a digital signature scheme must possess.

**Solution**:

A digital signature scheme must satisfy these six essential properties:

**1. Authenticity**: The signature is generated by the legitimate signer — the party holding the private key $PR_A$. No other party can produce a valid signature for Alice unless they possess $PR_A$.

**2. Integrity (Unalterability)**: A digital signature is computed over a hash of the message $H(M)$. Any modification to $M$ after signing changes $H(M)$, making the signature verification fail. Detects any tampering.

**3. Non-repudiation**: The signer cannot deny having signed the document. Since only the holder of $PR_A$ can create a valid signature, and $PR_A$ is uniquely associated with Alice, a valid signature is irrefutable evidence of Alice's intent. This is what makes digital signatures legally binding.

**4. Unforgeability**: It is computationally infeasible for any party without $PR_A$ to forge a valid signature on any message $M$. Security is based on the hardness of factoring (RSA) or discrete logarithm (DSA, ECDSA).

**5. Verifiability**: Any party with access to the signer's public key $PU_A$ can independently verify the signature — no secrets required for verification. This enables open verification by courts, auditors, and third parties.

**6. Not Reusable**: A signature is computationally bound to a specific document. It cannot be detached from one document and attached to another with the same validity. The hash binding makes this property enforceable — a signature on $H(M_1)$ cannot be the signature on $H(M_2)$ unless $H(M_1) = H(M_2)$ (collision — infeasible for strong hash functions).
