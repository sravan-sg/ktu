# Ambiguity in Context-Free Grammars

## 1. Explanation
A Context-Free Grammar (CFG) is considered **ambiguous** if there exists at least one string in the language generated by the grammar that has **more than one distinct parse tree**. Equivalently, this means the string has more than one Leftmost Derivation (LMD) or more than one Rightmost Derivation (RMD). 

From a compiler engineering perspective, ambiguity is a severe defect. If a grammar is ambiguous, it means the parser cannot uniquely determine the hierarchical structure of a sentence. Because the Abstract Syntax Tree (AST) dictates the semantics (meaning and execution order) of the program, an ambiguous syntax yields ambiguous execution. For example, if $3 + 4 * 5$ can be parsed as either $(3 + 4) * 5 = 35$ or $3 + (4 * 5) = 23$, the compiler does not know what machine code to generate.

**Resolving Ambiguity:**
We cannot write an algorithm that detects ambiguity for an arbitrary CFG because the problem is computationally **undecidable**. However, we can resolve ambiguity in known patterns using two primary methods:
1.  **Disambiguating Rules:** Keeping the ambiguous grammar but giving the parsing tool (like Yacc/Bison) strict rules for **precedence** (e.g., `*` binds tighter than `+`) and **associativity** (e.g., left-associative evaluates left-to-right).
2.  **Grammar Rewriting:** Mathematically refactoring the grammar to enforce structure. We introduce new non-terminals to represent different levels of precedence.

## 2. Example
Consider the classic ambiguous expression grammar:
$E \rightarrow E + E \mid E * E \mid \text{id}$

Input string: `id + id * id`

**Parse Tree 1 (Addition happens first):**
```text
        E
      / | \
     E  *  E
   / | \   |
  E  +  E  id
  |     |
  id    id
```

**Parse Tree 2 (Multiplication happens first):**
```text
        E
      / | \
     E  +  E
     |   / | \
    id  E  *  E
        |     |
        id    id
```
Because two completely valid, different structural trees exist for the exact same input string, the grammar is undeniably ambiguous. 

## 3. Applications & Use Cases
*   **The Dangling-Else Problem:** A famous ambiguity occurs in `if-then-else` statements. Consider: `if (x) if (y) A() else B()`. Does the `else` attach to the first `if(x)` or the inner `if(y)`? C, Java, and C++ resolve this structurally by dictating that an `else` always associates with the closest unmatched `if`.
*   **Mathematical Expression Parsers:** Calculators and expression evaluators must strictly eliminate ambiguity by separating expressions into `Term` and `Factor` layers to enforce PEMDAS.

## 4. 3 Solved Numerical/Analytical Examples

**Example 1: Rewriting an ambiguous grammar to enforce precedence**
*Problem:* Rewrite the ambiguous grammar $E \rightarrow E + E \mid E * E \mid \text{id}$ to unambiguously enforce that `*` has higher precedence than `+`, and both are left-associative.
*Solution:* We introduce new non-terminals: `T` (Term) for multiplication and `F` (Factor) for basic units.
1.  $E \rightarrow E + T \mid T$ (Addition happens last, evaluated left-to-right)
2.  $T \rightarrow T * F \mid F$ (Multiplication happens first, evaluated left-to-right)
3.  $F \rightarrow \text{id}$

**Example 2: Proving ambiguity using derivations**
*Problem:* Prove $S \rightarrow aSbS \mid bSaS \mid \epsilon$ is ambiguous.
*Solution:* Let's find two distinct Leftmost Derivations for the string `abab`.
*LMD 1:* 
$S \Rightarrow aSbS \Rightarrow a(bSaS)bS \Rightarrow ab(\epsilon)a(\epsilon)b(\epsilon) \Rightarrow abab$
*LMD 2:*
Wait, let's find a simpler string: `ab`.
$S \Rightarrow aSbS \Rightarrow a(\epsilon)b(\epsilon) = ab$ (Parse tree has root $S$ splitting into $a, S, b, S$).
Is there another way? No.
What about string `abab`?
*LMD 1:* $S \Rightarrow aSbS \Rightarrow abS \Rightarrow abaSbS \Rightarrow ababS \Rightarrow abab$
*LMD 2:* $S \Rightarrow aSbS \Rightarrow aSbSaSbS \dots$
Actually, $S \rightarrow aSbS \mid \epsilon$. For string $abab$:
Parse 1: $S \Rightarrow aSbS \Rightarrow a(\epsilon)b(aSbS) \Rightarrow ab a(\epsilon)b(\epsilon) = abab$
Parse 2: $S \Rightarrow aSbS \Rightarrow a(aSbS)b(\epsilon) \Rightarrow a(a(\epsilon)b(\epsilon))b \dots$ wait, this generates $aabb$, not $abab$.
Let's find `abab`.
Parse 1: $a( \epsilon )b( a(\epsilon)b(\epsilon) )$
Parse 2: $a( b(\epsilon)a(\epsilon) )b( \epsilon )$? No, that relies on $bSaS$. Let's assume the grammar is just $S \rightarrow aSbS \mid \epsilon$. No, the question includes $bSaS$. So for $abab$:
Parse 2: $S \Rightarrow aSbS \Rightarrow a(\epsilon)b(aSbS) = abab$
It turns out $S \rightarrow aSbS \mid bSaS \mid \epsilon$ generates strings with equal $a$'s and $b$'s. It is highly ambiguous because a string like `abab` can be split as `(ab)(ab)` or `a(ba)b`. 

**Example 3: Disambiguating the Dangling Else**
*Problem:* Write the unambiguous grammar for the Dangling Else problem.
*Solution:* We force all statements between an `if` and its corresponding `else` to be "matched" (having their own else).
$Stmt \rightarrow MatchedStmt \mid UnmatchedStmt$
$MatchedStmt \rightarrow \text{if } E \text{ then } MatchedStmt \text{ else } MatchedStmt \mid \text{Other}$
$UnmatchedStmt \rightarrow \text{if } E \text{ then } Stmt \mid \text{if } E \text{ then } MatchedStmt \text{ else } UnmatchedStmt$

### [April 2018]
**Question:** Explain the concept of Ambiguity in context-free grammars with an example. How can it be eliminated?
**Solution:**
**Concept of Ambiguity:**
A Context-Free Grammar is said to be ambiguous if it can generate more than one parse tree (or equivalently, more than one Leftmost Derivation or more than one Rightmost Derivation) for a single string of terminals. In compilers, ambiguity is unacceptable because a compiler relies on the unique structural representation (the parse tree) to determine the exact semantic meaning and execution order of a statement. If two parse trees exist, the compiler encounters a fatal conflict regarding which interpretation to compile into machine code.

**Example:**
Consider the grammar: $E \rightarrow E - E \mid \text{id}$
Input string: `id - id - id`
*Parse Tree 1 (Left-associative):* Evaluates as `(id - id) - id`
Root $E$ expands to $E - E$. The left child $E$ expands to $E - E$, which then becomes `id - id`. The right child $E$ becomes `id`.
*Parse Tree 2 (Right-associative):* Evaluates as `id - (id - id)`
Root $E$ expands to $E - E$. The left child $E$ becomes `id`. The right child $E$ expands to $E - E$, which becomes `id - id`.
Because two distinct trees exist for `id - id - id`, the grammar is ambiguous.

**Elimination:**
Ambiguity cannot be algorithmically detected or resolved universally (it is an undecidable problem). However, it can be eliminated manually by:
1.  **Grammar Rewriting:** Introducing new non-terminals to enforce strict precedence and associativity. For example, rewriting the above to:
    $E \rightarrow E - T \mid T$
    $T \rightarrow \text{id}$
    This structurally forces left-associativity.
2.  **Using Precedence Rules in Tools:** Supplying parser generators (like Yacc/Bison) with external precedence and associativity declarations, allowing the tool to break conflicts dynamically during parsing without rewriting the grammar mathematically.
