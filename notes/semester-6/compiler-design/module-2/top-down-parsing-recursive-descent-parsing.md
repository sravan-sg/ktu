# Top-Down Parsing: Recursive Descent Parsing

## 1. Explanation
Top-Down Parsing is a parsing strategy where the parser attempts to construct the parse tree from the root (the start symbol) down to the leaves (the tokens of the string). At each step, it attempts to find a leftmost derivation for the input string. 

**Recursive Descent Parsing** is the most intuitive implementation of top-down parsing. For every non-terminal in the grammar, the compiler engineer writes a dedicated recursive procedure (a function). The function's job is to recognize the language generated by that non-terminal. 

When the parser encounters a non-terminal $A$, it calls the function `A()`. Inside `A()`, it looks at the right-hand side of $A$'s productions. If the production contains terminals, it matches them directly against the current input token. If it contains other non-terminals, it calls their respective functions recursively.

However, a naive Recursive Descent Parser may suffer from two major flaws:
1.  **Backtracking:** If $A$ has multiple productions (e.g., $A \rightarrow aB \mid aC$), the parser might guess the first one, consume `a`, call `B()`, and if `B()` fails, it must "backtrack", un-consume `a`, and try the second production. Backtracking is computationally extremely expensive (often exponential time).
2.  **Left Recursion Infinite Loops:** If the grammar has a production of the form $A \rightarrow A \alpha$, the function `A()` will immediately call `A()` without consuming any input. This leads to infinite recursion and a stack overflow.

To build an efficient, production-grade parser without backtracking, we modify it to be a **Predictive Parser**, which looks ahead at the next token to make the correct choice instantly. We also mathematically eliminate left recursion from the grammar before writing the code.

## 2. Example
Consider a simple grammar without left recursion:
*   $S \rightarrow c A d$
*   $A \rightarrow a b \mid a$

The Recursive Descent C-pseudocode looks like this:
```c
void S() {
    if (lookahead == 'c') {
        match('c');
        A();
        match('d');
    } else { error(); }
}

void A() {
    if (lookahead == 'a') {
        match('a');
        // Backtracking problem: Do we expect a 'b' or are we done?
        if (lookahead == 'b') { match('b'); }
    } else { error(); }
}
```

## 3. Applications & Use Cases
*   **Production Compilers:** Despite the existence of automated parser generators (like Bison), many real-world compilers (including GCC, Clang for C++, V8 for JavaScript, and the Go compiler) use hand-written Recursive Descent parsers. Why? Because writing it by hand allows for highly sophisticated, custom error recovery and beautiful, user-friendly error messages that automated table-driven parsers struggle to provide.
*   **JSON/XML Parsers:** Lightweight data serialization libraries often implement recursive descent because it is memory-efficient and requires no external code-generation dependencies.

## 4. 3 Solved Numerical/Analytical Examples

**Example 1: Eliminating Direct Left Recursion**
*Problem:* Eliminate left recursion from the expression grammar $E \rightarrow E + T \mid T$.
*Solution:*
The general formula to eliminate $A \rightarrow A\alpha \mid \beta$ is to rewrite it as:
$A \rightarrow \beta A'$
$A' \rightarrow \alpha A' \mid \epsilon$
Applying this to $E$:
Here $\alpha = + T$ and $\beta = T$.
*   $E \rightarrow T E'$
*   $E' \rightarrow + T E' \mid \epsilon$
This allows the parser function `E()` to call `T()` first, consuming input before recurring on `E'()`, avoiding the infinite loop.

**Example 2: Eliminating Left Factoring**
*Problem:* Eliminate the backtracking issue (Left Factoring) from $S \rightarrow i E t S \mid i E t S e S \mid a$.
*Solution:*
Both productions share the common prefix $i E t S$. A predictive parser wouldn't know which to choose. We factor out the common prefix.
Let $\alpha = i E t S$, $\beta_1 = \epsilon$, $\beta_2 = e S$.
*   $S \rightarrow i E t S S' \mid a$
*   $S' \rightarrow \epsilon \mid e S$

**Example 3: Tracing a Recursive Descent Execution**
*Problem:* Trace the function calls for the grammar $S \rightarrow x Y$, $Y \rightarrow y$, parsing the string `xy`.
*Solution:*
1.  Parser starts by calling `S()`.
2.  `S()` checks the first token `x`. It matches. Consumes `x`. Input is now `y`.
3.  `S()` calls `Y()`.
4.  `Y()` checks the token `y`. It matches. Consumes `y`. Input is empty.
5.  `Y()` returns to `S()`.
6.  `S()` returns successfully. String accepted.

### [April 2018]
**Question:** Explain recursive descent parsing. What are the problems associated with top-down parsing?
**Solution:**
**Recursive Descent Parsing:**
Recursive descent parsing is a top-down parsing technique where the compiler engineer constructs a set of mutually recursive functions (procedures) to process the input. There is exactly one function for each non-terminal in the grammar. The execution begins with the function corresponding to the start symbol. Inside the function for non-terminal $A$, the code examines the current input token to decide which production rule $A \rightarrow \alpha_i$ to apply, and then executes code to match terminals in $\alpha_i$ or recursively call functions for non-terminals in $\alpha_i$.

**Problems associated with Top-Down Parsing:**
1.  **Left Recursion:** If the grammar contains a production like $A \rightarrow A \alpha$, the top-down parser will enter an infinite loop. The function `A()` will invoke `A()` again before consuming any input tokens, leading to a stack overflow. The grammar must be mathematically rewritten to eliminate left recursion before a top-down parser can be built.
2.  **Backtracking:** If a non-terminal has multiple productions sharing a common prefix (e.g., $A \rightarrow a b c \mid a b d$), the parser might make a wrong guess, consume $a$ and $b$, realize $c$ is not the next token, and be forced to reverse its state, backtrack the input pointer, and try the other production. Backtracking makes parsing extremely slow (exponential time complexity).
3.  **Left Factoring Requirement:** To avoid backtracking, the grammar must undergo Left Factoring, a process where common prefixes are factored out into new non-terminals so that the parser can delay its decision until the distinguishing token is reached.
